# Design decisions

Why the workflow is shaped the way it is. Several of these were settled by running it on a real n8n rather than decided up front, and those say so.

## 1. A visible cascade, not a loop in one Code node

One Code node could hold the provider list and loop over it. It would be shorter, and adding a provider would be one line.

It would also hide the part that matters. In the editor, the cascade shows at a glance which provider is tried when and where a failure goes. The HTTP nodes use n8n's credential store, which a Code node cannot use cleanly, so the keys would end up in code. And each failure path is a real error output that the executions view shows node by node.

The cost is four nodes per provider. For three providers, that is the right trade.

## 2. The error output loses the item, so the failure handler rebuilds it

An error output carries only `{ error }`. Wire an HTTP node's error output straight into the next provider and that provider receives no conversation and no availability flags: the cascade stops at the first failure while looking correct on the canvas.

Every *record failure* node therefore re-reads the conversation from *Validate request* with `$('Validate request').first()`. That is the one reference that holds the same data whichever path the execution took.

This is the decision the whole workflow depends on, and the easiest one to get wrong.

## 3. Classify from structured fields, never from the text of the error

**Found while testing on n8n 2.40:** the first version searched the whole error, serialised, for status codes. The error includes the stack trace, and the stack trace includes line numbers such as `events:521:24`. Every failure, a rejected key included, looked like a 5xx and put the provider to rest.

The handler now reads `status` and `code` only, and matches words only in the message. A test feeds it a 401 whose stack contains `521`.

## 4. Cooldowns sized by cause

- **Quota, 30 minutes.** A 429 can mean a per-minute limit or a daily one. n8n's error item carries no `Retry-After` and no response headers, so the workflow cannot tell which. Thirty minutes is short enough not to waste a per-minute limit for long, and long enough not to hammer a daily one.
- **Outage, 5 minutes.** Server errors and timeouts usually clear quickly, and every request that tries a dead provider pays the full timeout.
- **Rejected or bad response, none.** A bad key or an unknown model is fixed by changing the configuration, not by waiting; a rest would only delay the fix. An empty answer is often a one-off.

## 5. A turn is saved only after an answer

*Validate request* builds the history as a copy. The session in static data changes only in *Save turn*, after a provider has answered.

Otherwise a message that no provider could answer stays in the history, the next request sends two user messages in a row, and every later reply is slightly off without anyone knowing why.

## 6. No default session

A missing session id is a 400, not a fallback to a shared `default` session. A fallback means that every client which forgets the id reads and writes the same conversation, which is a privacy failure disguised as convenience.

The id is generated by the client, once per visitor.

## 7. The system prompt lives only in the workflow

Accepting a prompt from the request would turn the endpoint into a general-purpose proxy to three free tiers, with the operator's quota and the caller's instructions.

## 8. Origins are checked in the workflow, and configured once

CORS stops a browser from reading a response. It does not stop the request, which still runs and still spends quota. So *Validate request* refuses browsers from other sites itself.

It reads the allowed list from the Webhook node's own *Allowed Origins* setting rather than keeping a copy, so the two cannot drift apart. Callers that send no `Origin` header, such as a server or `curl`, are not browsers and are governed by the rate limits instead.

## 9. Static data, not a Data Table

Static data needs no setup: import, add keys, publish. A Data Table needs a table created by hand with the right columns before the workflow can run.

**The cost, measured on n8n 2.40:** an execution reads static data when it starts and writes all of it back when it ends, after the webhook has already answered. A request that lands in that gap reads the old state and then overwrites the new one. In 540 sequential requests it never happened. In 2 of 4 end-to-end runs made while the machine was busy with other work, it cost a provider's cooldown. Once the suite paced its requests like a person typing, 5 runs out of 5 passed.

For a chat that people type into, the worst case is one extra call to a resting provider. For concurrent traffic, sessions and cooldowns belong in a Data Table or an external store, and that is the first change I would make.

## 10. Bounded by design

Sessions expire after 24 hours of inactivity, at most 100 are kept, and each keeps the 24 messages that are also sent to the model. The n8n documentation asks for static data to stay small, and a store that only grows eventually becomes a slow workflow nobody can explain.

Housekeeping runs at the start of every request, so no scheduled job is needed.

## 11. Successful executions are not saved

By default n8n stores every execution, input and output, which here means a second copy of every conversation in the execution log, kept for as long as the log is.

Failed executions are still saved, and they are the ones worth debugging. For a closer look at the successful ones, the setting can be turned on for a while.

## 12. Provider order

Gemini first and OpenRouter's free router last. The router sends each request to whichever free model is available, so answers vary in style and quality from one call to the next. It is the right last resort and the wrong first choice.

Gemini is called through the `gemini-flash-latest` alias. Free-tier model names are retired often, and a pinned name that disappears turns into a permanent `rejected`. The alias trades reproducibility for staying up; a production deployment should pin a version and update it on purpose.

## 13. The 503 names the failure, not its message

The caller learns which provider failed last and why (`quota`, `outage`, `rejected`, `bad_response`). The message itself stays in n8n: provider errors can echo parts of the request or details of the account.

## 14. Per-IP limits belong at the proxy

The workflow sees the request headers, and `X-Forwarded-For` is whatever the client or the chain of proxies wrote there. A limit keyed on it is either bypassable or, behind a CDN, a single shared bucket. The reverse proxy knows the real address, so that is where the limit goes.

## 15. The code lives in `src/`, the export is generated

The workflow export is a JSON file with the JavaScript stored as escaped strings: unreadable in a review and impossible to diff meaningfully. The Code nodes are therefore kept in `src/` as plain JavaScript and copied into the export by `scripts/sync-code.mjs`, with `__PROVIDER__` filled in per provider.

CI runs the copy in check mode, so an export that does not match the reviewed code fails the build.
